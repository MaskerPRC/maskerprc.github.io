基于 PyTorch、TorchAudio 和 Flashlight Text 的快速束搜索解码

由 Caroline Chen，Jacob Kahn (@jacob_d_kahn)撰写

从 Flashlight Text（Flashlight 机器学习框架的一部分）以行业领先的解码速度进行束搜索，现在在 TorchAudio 中提供官方支持，为基于 PyTorch 的语音和文本应用提供高性能束搜索和文本工具。当前集成支持 CTC 样式解码，但可用于任何输出时间步长上 token 级概率分布的建模设置 。

简要回顾束搜索

在语音和语言设置中， 束搜索是一种高效的贪婪算法，可以将连续值序列（即概率或分数）转换为图或序列 （即标记、词片段、单词），使用可选的有效序列约束 （即词典）、 可选的外部评分 （即对有效序列进行评分的 LM）和其他针对特定序列的评分调整 。

在下面的例子中，我们将考虑一个标记集 {ϵ, a, b}，其中 ϵ 是一个特殊标记，我们可以想象它表示单词之间的空格或语音中的停顿。此处及以下图形均来自 Awni Hannun 关于 CTC 和 beam search 的优秀 distill.pub 写作 。

采用类似贪婪的方法，beam search 考虑给定现有标记序列的下一个可行标记——在上面的例子中，a, b, b 是一个有效序列，但 a, b, a 则不是。我们在 beam search 的每一步根据评分函数对每个可能的下一个标记进行排名。评分函数（s）通常看起来像这样：

ŷ是一个潜在的路径/标记序列，x 是输入，(P(ŷ|x) 代表模型随时间预测的结果，𝛼是语言模型概率 (P(y) 序列在语言模型下的概率)的权重。一些评分函数添加了 𝜷，根据预测序列的长度 |ŷ| 调整分数。这个特定的评分函数用于 FAIR 在端到端 ASR 方面的先前工作，并且评分函数的许多变体可以在不同的应用领域有所不同。

给定一个特定序列，为了评估该序列中的下一个可行标记（可能受一组允许的单词或序列，如单词词典的限制），束搜索算法会为每个添加的候选标记对序列进行评分，并根据这些评分对标记候选进行排序。由于路径数量与标记集大小呈指数关系，因此只保留评分最高的前 k 个候选标记——其中 k 代表束大小 。

束搜索的进展还有许多其他细微之处：例如，相似的反向序列可以被“合并”。

分数函数可以进一步调整对插入或长或短单词的权重。使用更强的外部语言模型进行评分，虽然会增加计算成本，但也可以显著提高性能；这通常被称为 LM 融合 。解码还有很多可调整的参数——这些在 TorchAudio 的文档中有详细说明，并在 TorchAudio 的 ASR 推理教程中进一步探讨。由于解码效率很高，参数可以轻松调整和优化。

这些年，在 ASR 领域，已经广泛使用了束搜索，涉及的工作太多，难以一一列举，包括 wav2vec 2.0 和 NVIDIA 的 NeMo 等强大、最新的结果和系统。

为什么使用束搜索？

束搜索一直是快速解码方法的强劲竞争对手，如 Google 投入资源将其部署到设备上的 RNN-Transducer，并在常见基准上取得了显著成果。大规模的自回归文本模型也可以从束搜索中受益。束搜索还有其他优点，例如：

  • 可灵活调整性能/延迟权衡——通过调整搜索宽度和外部语言模型，用户可以牺牲延迟以换取准确性，或者以微小的延迟成本获得更准确的结果。不使用外部语言模型进行解码可以在几乎不牺牲性能的情况下提高结果。
  • 无需重新训练即可实现便携性——现有的神经模型可以受益于多种解码设置，并且可以与外部语言模型即插即用，无需训练或微调。
  • 吸引人的复杂度/准确性权衡——将束搜索添加到现有的建模流程中只会增加很少的额外复杂度，并且可以提高性能。

性能基准

目前最常用的支持外部语言模型集成的束搜索解码库包括 Kensho 的 pyctcdecode、NVIDIA 的 NeMo 工具包 。我们使用在 100 小时音频上训练的 wav2vec 2.0 基础模型，在 LibriSpeech dev-other 上进行评估，与官方的 KenLM 3-gram 语言模型进行基准测试。基准测试在 Intel E5-2698 CPU 的单线程上运行。所有计算都在内存中进行——禁用了 KenLM 内存映射，因为它没有得到广泛支持。

在基准测试中，我们测量的是时间到词错误率（WER）——由于解码算法实现的细微差异以及参数与解码速度之间的复杂关系，一些超参数在运行中有所不同。为了公平地评估性能，我们首先对达到基线 WER 的参数进行扫描，尽可能最小化搜索宽度。

预训练的 wav2vec 2.0 模型在 Librispeech dev-other 上的解码性能。在低 WER 下，TorchAudio + Flashlight 解码器比其他解码器性能高出一个数量级。

时间到词错误率结果，在较小的搜索宽度下，跨解码器。TorchAudio + Flashlight 解码器在较大的搜索宽度和较低的词错误率下具有更好的扩展性。

TorchAudio API 和用法

TorchAudio 提供 Python API 进行 CTC 束搜索解码，支持以下功能：

  • 词典和词典自由解码
  • KenLM n-gram 语言模型集成
  • 字符和词元解码
  • 样本预训练的 LibriSpeech KenLM 模型以及相应的词典和标记文件
  • 可自定义的各种束搜索参数（束大小、剪枝阈值、LM 权重等）

设置解码器时，请使用 torchaudio.models.decoder.ctc_decoder 工厂函数

from torchaudio.models.decoder import ctc_decoder, download_pretrained_files
files = download_pretrained_files("librispeech-4-gram")
decoder = ctc_decoder(
   lexicon=files.lexicon,
   tokens=files.tokens,
   lm=files.lm,
   nbest=1,
   ... additional optional customizable args ...
)

给定形状为 (batch, time, num_tokens) 的发射，解码器将计算并返回一个包含 batch 个列表的列表，每个列表包含对应发射的 nbest 假设。每个假设可以进一步分解为标记、单词（如果提供词典）、得分和时序组件。

emissions = acoustic_model(waveforms)  # (B, T, N)
batch_hypotheses = decoder(emissions)  # List[List[CTCHypothesis]]

# transcript for a lexicon decoder
transcripts = [" ".join(hypo[0].words) for hypo in batch_hypotheses]

# transcript for a lexicon free decoder, splitting by sil token
batch_tokens = [decoder.idxs_to_tokens(hypo[0].tokens) for hypo in batch_hypotheses]
transcripts = ["".join(tokens) for tokens in batch_tokens]

请参阅文档以获取更多 API 详细信息，以及教程（ASR 推理解码 ）或示例推理脚本以获取更多使用示例。

即将推出的改进

全面支持 NNLM — 在大规模上使用大型神经语言模型（例如，transformers）的解码仍处于某种程度上的未充分探索。Flashlight 已支持，我们计划在 TorchAudio 中添加支持，使用户能够使用兼容自定义解码器的 LM。自定义词级语言模型已在 TorchAudio 的夜间构建中提供，并计划在 TorchAudio 0.13 版本中发布。

自回归/seq2seq 解码 — Flashlight Text 还支持自回归模型的序列到序列（seq2seq）解码 ，我们希望为其添加绑定，并将其与 TorchAudio 和 TorchText 一起添加，以实现高效的 GPU 实现。

更好的构建支持 — 为了从 Flashlight Text 的改进中受益，TorchAudio 将直接将 Flashlight Text 作为子模块，以便更容易地进行上游修改和改进。这一改动已在夜间 TorchAudio 构建中生效，并计划在 TorchAudio 0.13 版本中发布。
